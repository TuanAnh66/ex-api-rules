Troubleshooting Your API Requests

REST error response​

Every error response of the Payments API has the same format and contains exactly one error:

{
  "code": 7004,
  "error_message": "TRANSFER_INSUFFICIENT_FUNDS",
  "description": "Insufficient funds on the source account. Check the balance, then fund the source account or reduce the amount."
}
FieldTypeUse
codeintegerStable numeric business code. Use it in your error handling.
error_messagestringStable public name of the error. Use it in your error handling and logs.
descriptionstringShort human-readable hint. The text may change without notice; do not parse it.

The HTTP status describes the transport and API layer. code and error_message identify the exact problem.

Payments API error codes​

The Retry column describes automatic retries. No means that repeating the request without fixing the cause will not help; it does not prevent you from sending a corrected request. After fixing authentication or permissions, resend the same transfer request with the same idempotency key. After a rate-limit error, wait and reduce the request rate before resending.

For transfer creation, the client actions apply while no request sent with the idempotency key has had an unknown outcome. After an unknown outcome, an error on a retry leaves the outcome unknown: do not change the request or the key to get past the error. Follow Recovery and idempotency to decide whether to resend, fix the cause, or close the record and check Transaction History.

Operations: Create — POST /v1/transfers; Balance — GET /v1/accounts/{account_id}/balance; Status — GET /v1/transfers/{transfer_id}.

Best practices for handling errors​

  • •

    Branch on the code

    Use code or error_message, never description or the HTTP status alone.

  • •

    Check before retrying

    Use automatic retries only where the table allows them. Otherwise, fix the cause first and follow the recovery rules for transfer creation.

  • •

    Reuse the key on retries

    For every retry of a creation request, reuse the same idempotency key and the exact same request.

  • •

    New key only for a new transfer

    Use a new idempotency key only for a new transfer, after the outcome of the previous attempt is confirmed. If you stop sending a transfer without a 201, retire its key first.

  • •

    Record before sending

    Save the idempotency key, request, state, and attempt time before sending. Keep this record across restarts; do not send the request if saving fails.

  • •

    Log for reconciliation

    Log code, error_message, the idempotency key, and the transfer_id if you have one, so that you can reconcile every attempt.

Authentication and permission checklist​

For AUTH_INVALID_API_KEY and AUTH_INVALID_SIGNATURE, follow the checks in Request signing. Checks specific to the Payments API:

  • For GET requests, EXN-IDEMPOTENCY-KEY is present with an empty value, and the signed idempotency_key is an empty string.
  • For POST /v1/transfers, the signed idempotency_key is the same UUID as in EXN-IDEMPOTENCY-KEY.
  • The signed path contains account_id or transfer_id exactly as sent in the request path.

For AUTH_PERMISSION_DENIED, check:

  • The key has the scope for the operation: Internal transfers for transfers between your own accounts, Partner transfers for transfers to another client. See Payments scopes.
  • The request comes from a source IP that is allowed for the key.

The complete signing rules are described in Request signing.

Idempotency and recovery​

Unknown outcome

After a timeout, no response, a non-API response (an HTML page, or a JSON body from a proxy or load balancer), TRANSFER_OUTCOME_UNKNOWN, SYSTEM_INTERNAL_ERROR, or SYSTEM_TEMPORARY_UNAVAILABLE, the outcome is unknown: resend the exact same request with the same idempotency key. Before every creation request, record durably that it is being sent, and send the requests of one transfer from one sender at a time.

Errors on a retry

An error on a retry after an unknown outcome does not show whether a transfer exists. Do not change the request or the key to get past it.

If you stop resending without a 201, retire the key first, so that no restart or pending resend sends it again. Then check Transaction History, and use a new key only after Customer Support confirms that no transfer was created.

The complete procedure is described in Recovery and idempotency.
