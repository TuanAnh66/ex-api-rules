# Architecture and boundaries

- catalog/: editable rules, official source allowlist, check–test registry. Authoring status is draft; changing this directory never changes an approved bundle.
- schemas/: language-neutral JSON Schema 2020-12 contracts; copied verbatim into the core package by build.
- packages/core/: canonicalization, integrity, schemas, profile selection and report serialization. It imports neither filesystem/crawler nor JavaScript syntax parsers.
- packages/cli/: filesystem, public HTTP collector, external store and language adapters. JavaScript is the first adapter; unsupported files are hashed and reported as unanalyzed.
- Review input uses a deterministic per-file/aggregate byte budget and bounded chunk reads. Unsupported files stream into a digest without full buffering; over-budget/changed/incomplete reads publish no partial hash. File states and check execution/applicability feed report v2 independently of findings. Core validates v1/v2 reports and pure consistency/fingerprint rules; CLI retains all filesystem/stat/parser work. Report v1, portable and lock contracts remain unchanged.
- agents/: human/agent interpretation and mandatory behavioral checklist. The agent does not repair reviewed code.
- tests/fixtures/: sanitized offline cases and language-neutral vectors.
- .github/: offline CI, PR checklist, CODEOWNERS, manually dispatched release.

A rule describes a requirement; a check describes one way of finding violations. catalog/checks.json maps checks to stable IDs and regression cases. No check or schema claims complete business correctness. Retired rules retain IDs; superseded rules point to a successor. Inference is excluded from conformance selection.

CLI Git subprocesses use one invocation helper, require Git 2.36+, override core.fsmonitor=false, and use an isolated Git configuration environment. Repository selection always follows the resolved target project; inherited GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE and other GIT_* values cannot redirect review. Git diff also disables external diff and text conversion. The version check runs before repository inspection commands. This reduces known execution/configuration paths without claiming a sandbox against every repository-local Git feature.

## Mutable data outside installation

Default store: EX_API_RULES_DATA_DIR, otherwise Windows LOCALAPPDATA/ex-api-rules or XDG_STATE_HOME/ex-api-rules (~/.local/state/ex-api-rules on other systems). Override with --data-dir. CLI refuses a store/output inside its installation or submodule.

CLI write guards resolve the nearest existing parent before any creation and recheck individual writes. Runtime destinations must use physical paths: symlink/junction aliases, dangling links, private paths and submodule gitfiles are rejected. Ordinary worktrees with conventional `.git/worktrees/<name>` metadata remain supported; unrecognized gitfiles fail closed. A project cache cannot be redirected by a link, and an installed package does not protect its entire consuming workspace as if it were the tool checkout. These checks do not provide an OS-level guarantee against a concurrent hostile filesystem replacement between check and write.

Store layout: blobs/<prefix>/<SHA-256>, bundles/<artifactSHA>.json, bundles/index.json, candidates/<ID>, approvals/a-<candidateIdSHA256>.json, maintainer-active.json, cache/checks/<ID>, cache/views/<artifactSHA>, cache/latest-<artifactSHA>.json. Bundle IDs and recorded candidate identities cannot be rebound. Import never activates a bundle. Import and the entire approval transaction share bundles/write.lock; caught errors normally release it, while process termination or release failure can leave a visible lock requiring maintainer inspection. Disposable views are verified against content hashes.

An immutable approval envelope checksums its record with utf16-v1 canonical JSON. The active pointer includes the approval ID and checksum, and the record includes its exact bundle, candidate artifact, reviewer, timestamp, baseline and previous active pointer. Readers validate pointer fields before constructing a record path, then verify the record, artifacts and history chain. Artifact/index writes and approval fsync precede active pointer replacement. An unreferenced record is a prepared orphan, not a committed activation. The current verified pointer and its ancestry define committed history; retrying an ancestor never rolls back a newer active bundle. An orphan can commit only while its recorded baseline is still current. No automatic stale-lock clearing or legacy runtime-pointer migration occurs. Original portable bundles and consumer project locks retain their identities.

Collection compares the union of rule IDs, with structural added/removed/changed/unchanged and before/after records. Unchanged structure is not semantic source approval. Approval enforces retained historical IDs, stable scope/kind/introducedIn, monotonic revisions (increased for a changed rule/lifecycle), and existing acyclic superseded successors. This uses the verified maintainer baseline, or the exact preserved v0.1.0 baseline from the checkout/imported release for the first approval; unrelated imported bundles do not implicitly establish a lineage.

File contents are fsynced before rename; POSIX directory entries are fsynced, including new directory parents. Node on Windows has no portable directory fsync here. The protocol detects synchronous pre/post-commit failures but does not claim an OS transaction, guaranteed power-loss durability on every filesystem, or protection against a concurrent hostile filesystem replacement. Error state after pointer publication is explicitly committed, not committed, or unknown; maintainer recovery rules are in docs/maintainers.md.

Each target project owns .ex-api-rules.lock.json and .cache/exness-rules reports. Lock selects exact tool version, bundle ID, bundle hash, portable artifact hash, schema version and profile. Two projects can select different bundles and source-check timestamps using one store. A mismatching tool/profile/bundle errors until explicitly pinned. Review never updates the lock.

HTML source comparison keeps separate prose, anchor/href and pre/code evidence. Raw hrefs, anchor/context, resolved URLs, code language/example hints and exact parsed code text remain available in before/after deltas. Relative links resolve against the source's final URL and an HTML base href when present, including when identical snapshot bytes move to a different URL. Discovery uses those resolved links through the existing public URL allowlist. Presentation requires unchanged evidence projections; code whitespace is never globally collapsed. Changed links/code or labelled example content are requires-review, while changed normative prose is technical. Example markers are evidence metadata, not guarantees of harmlessness. Content outside the selected article is excluded except base URL metadata affecting article links. Stable redirect context remains unchanged. Check reports expose reviewRequired and a corresponding summary count; flagged examples/moves/failures cannot be counted as nonTechnical. These labels guide human triage and do not establish semantic correctness or update any approval/pin.

## Migration and distribution

Tool 0.2.0 packages and schema version 2 portable envelopes wrap the original schema version 1 manifest/rules without changing their bytes or bundle hash. Only the exact legacy hash is allowed to lack new lifecycle fields. New approved bundles require lifecycle metadata.

Canonical digests use an explicit manifest algorithm for new collections (`utf16-v1`); absent markers retain the historical `ecmascript-v0` order for both bundle and portable-artifact hashes. See docs/protocol.md. No import or review rewrites an existing bundle or lock to change its algorithm.

Legacy snapshots remain in Git for v0.1.0 compatibility. New snapshots live in external content-addressed storage and portable release assets. Git carries authoring rules, source catalog, release descriptors, citations and review decisions. Importing a release verifies hashes but does not establish trust in its author: obtain assets/checksums from a reviewed maintainer release.

Submodule pinning and project rule locks serve different purposes. Updating a Git pointer does not approve a candidate or upgrade a project's locked tool/bundle. No background server or scheduler is required.
