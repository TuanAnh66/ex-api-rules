# Portable protocol

Schemas use JSON Schema 2020-12. Schema URNs are stable contract identifiers (the bundle contract URN :1 defines the first portable contract whose envelope schemaVersion is 2). Lock/catalog/rule/check contracts use version 1 where present. Historical report v1 remains urn:ex-api-rules:report:1 in report.schema.json; the current writer uses schemaVersion:2 and urn:ex-api-rules:report:2 in report-v2.schema.json. Tool version uses SemVer independently of bundle identity. Future incompatible contracts need new schema identifiers and migration support.

Canonical JSON (`utf16-v1`): recursively sort object property names by UTF-16 code units, including integer-like keys (`"10"` precedes `"2"`), retain array order, encode with ECMAScript JSON string escaping, omit whitespace and trailing newline. Strings are not Unicode-normalized. Protocol numbers must be safe integers; decimal quantities use strings. Missing/undefined, sparse array slots, NaN and infinite values are not protocol values. `core.stringify` emits this order directly; `JSON.stringify(core.canonical(value))` is not a substitute because JavaScript reorders integer keys. Non-JavaScript readers should implement these rules rather than rely on their language's defaults. tests/fixtures/protocol-v1.json and check-protocol.py cover nested integers, the array-index boundary and UTF-16 ordering.

Digest compatibility is explicit in `manifest.canonicalization`. New collections declare `utf16-v1`. An absent field means the historical `ecmascript-v0` algorithm; explicit `ecmascript-v0` is also supported. That algorithm first sorts names by UTF-16, then emits ECMAScript array-index keys (canonical decimal names from `0` through `4294967294`) before all other keys, in numeric order, at every object. `core.legacyStringify` implements it and `core.bundleStringify(manifest, value)` selects the declared algorithm; unknown names are rejected. Both bundleHash and artifactSha256 use this selection. Existing unmarked bundles, stored artifact paths and locks retain their original digests. Verification never guesses an algorithm from a matching hash or adds a marker to imported bundles. The preserved v0.1.0 bundle remains unmarked and unchanged. A new collection is required to opt into the new algorithm; no project lock is upgraded automatically. Review fingerprints identify their independent `utf16-v1` algorithm in report metadata.

A portable envelope has schemaVersion:2, manifest, rules and blobs. Each blob key is its raw-byte SHA-256; its value is canonical RFC 4648 base64 with padding. Exactly the referenced source/local-evidence hashes must be included. Source records retain URL, fetched time, SHA-256 and relative snapshot path. Rules retain stable IDs, kind, scope, statement, evidence and lifecycle. Evidence can cite sourceId with pointer/terms or a sanitized local snapshot/hash. Missing IDs, conflicting references, successors or corrupt blobs invalidate the bundle. Anchor matching is a separate CLI check, never proof of semantic equivalence.

bundleHash = SHA-256(selected canonical JSON of {sources:manifest.sources,rules}). artifactSha256 = SHA-256(selected canonical JSON of the entire portable envelope). SHA256SUMS instead hashes the exact downloaded file bytes (including formatting/newline). These digests have distinct purposes. A hash establishes integrity; maintainer review establishes intended trust.

The legacy manifest ID is the original candidate ID; reports retain its historical approved version v-<candidate>-<hash-prefix>. New approvals assign manifest IDs v-<candidate>-<hash-prefix>. No legacy source, rule or manifest file is rewritten.

Rule lifecycle: draft -> in_review -> approved; deprecated/superseded remain available for history but are excluded from conformance checks. Superseded requires supersededBy. approved inference remains inference, never an enforceable requirement. Observations include date, scope and sanitized provenance. Preserve contradictions as separate evidence.

Collection ruleChanges compares the union of IDs with structural added/removed/changed/unchanged and explicit before/after (null on the absent side). semanticSourceReviewRequired remains true; structural equality does not establish semantic equivalence of fetched sources. Approval against the current maintainer lineage retains all historical IDs, checks scope/kind/introducedIn stability and revision progression, and rejects missing/cyclic successors. These are maintainer workflow constraints, not new Exness trading requirements. Store-local approval envelopes and active-pointer recovery are described in docs/maintainers.md; portable schemaVersion and legacy bundle bytes/hashes are unchanged.

HTML source changes expose reviewRequired, linkChanges, codeChanges, exampleChanges and documentContext. Delta entries use added/removed/changed with before/after (null for absence); positions identify occurrences, not persistent rule IDs. Link evidence retains raw href, resolvedHref (null when unresolved), anchor text and prose context. Code evidence retains exact parser-decoded text, block/inline kind, language and example hints; it does not execute code or claim browser/CSS equivalence. requires-review marks link/code/example changes whose meaning needs human assessment. presentation requires unchanged tracked projections. Source URL/redirect context is compared across both records, so a stable redirect alone is not a new move. Report summary.reviewRequired counts flagged changes and overlaps technical/failed counts; nonTechnical excludes every flagged change, including OpenAPI examples. These report additions do not modify raw snapshots, bundle canonicalization or portable digests.

JSON review reports are the primary machine interface. Findings include ruleId, file, line, severity, kind, evidence and recommendation. SARIF 2.1.0 preserves rule IDs, location, evidence and fingerprints. A stable result fingerprint is reproducible for identical code/tool/bundle/profile; timestamps and source freshness remain metadata. Unsupported adapters and failed parsing are manual review, never pass.

Report v2 adds strict codeVersion, inputPolicy, findings/evidence, manualChecks and coverage contracts without changing the v1 URN or schema bytes. core.validate('report', value) dispatches versions 1/2; v2 also validates referential consistency (selected rules, analyzed file locations, check mappings/statuses, byte accounting and manual coverage). core.toSarif accepts both versions and carries v2 file states/policy as run properties. For both v1 and v2, SARIF error level uses the CLI's documented+P1 predicate; observations remain warnings. This corrects the historical observed+P1 output policy without rewriting any saved v1 report, fingerprint, schema or URN. The permissive v1 reader remains available; there is no implicit v2-to-v1 downgrade. Build/package resources include both schemas; report-protocol-v2.json supplies language-neutral v1/v2 examples and malformed v2 mutations alongside protocol-v1.json. The Python reference consumer verifies the v2 complete-file hash and canonical fingerprint offline when Python is available.

File records distinguish analyzed, unsupported, parse-failed, analysis-failed, budget-exceeded, read-failed, changed-during-read, missing, not-regular and excluded. adapterStatus distinguishes completed, parse-failed, failed and not-run. sha256 is a complete digest or null; hashStatus is complete/not-computed. Completed hashing alone does not establish analysis. bytesRead counts confirmed bytes, while budgetBytesCharged conservatively reserves a failed read's requested bytes. The bounded-reader policy is serialized in inputPolicy, including stable path order, limits and explicit/base/ignore/private selection. Rule inventory and checkApplicability are independent of finding count, and no state is called compliant/pass.

The v2 fingerprint is SHA-256(utf16-v1 canonical JSON of {schemaVersion,toolVersion,ruleVersion,bundleHash,artifactSha256,profile,codeVersion,inputPolicy,findings,manualChecks,coverage,conflicts,limitations}). createdAt and sourceFreshness are excluded. A null file hash cannot bind unknown file contents: this fingerprint covers observed inputs/configuration/conclusions, not unobserved bytes. Existing portable bundle/lock digests and their algorithm selection remain unchanged. Report v2 is an unreleased development change; retained 0.2.1 metadata must not be used to replace or republish the existing release.
