# User operations

Install the two tarballs from GitHub Releases together as shown in README. Use the bundled executable via npx --no-install so an absent package is never fetched implicitly. The core library is also usable without CLI; Python/Go consumers use the same JSON schemas, protocol and fixtures.

From ExTransfer use node tools/exness-rules.cjs; from a standalone checkout use its own tools/exness-rules.cjs. --project-root defaults to the current working directory unless a project wrapper supplies it. Files are relative to that target. --base resolves a Git commit there and reviews changed/untracked public files; deleted files are not analyzed. It explicitly records excluded private paths and unsupported languages. Explicit private paths are rejected before reading.

Review requires Git 2.36 or newer, including when --files is used to record the target HEAD. Each review invokes Git with fsmonitor disabled, external diff/text conversion disabled for diff, and a separate subprocess environment that ignores inherited GIT_* settings and system/global Git configuration. No persistent Git configuration is changed. Target-local configuration still exists; these controls are not a sandbox for arbitrary hostile Git repositories. A project without Git metadata records HEAD as unavailable.

Before first review import the bundle and pin it. A repository checkout can bootstrap the preserved v0.1.0 bundle for older wrapper calls; reports say legacy-compatibility-unlocked until you run pin. A package installation cannot bootstrap missing snapshots: import the release artifact instead. Never treat an unlocked compatibility review as a reproducible lock.

Commit your .ex-api-rules.lock.json. Keep .cache/exness-rules ignored. A review records target HEAD and file hashes, tool/bundle/schema versions, source freshness, profile, findings and missing checks. resultFingerprint excludes timestamps but covers code, selected rules and conclusions. Use --format sarif for CI; still read JSON/manual checks because no findings does not prove compliance. CI can upload the SARIF using GitHub's supported upload action if repository permissions allow it.

The JavaScript adapter blocks only selected request-context violations: a recognized unshadowed global fetch to a literal Exness Gateway URL, a fully known inline JSON transfer body, or a directly encoded EXN-DATA object with a provable path/body mismatch. Object spreads and duplicate keys follow overwrite order. Unresolved spreads, accessors, computed keys, custom serialization, aliases, helper calls and shadowed globals require manual review. UUID and ACK patterns are manual checks: names alone establish neither retry identity nor final execution. Ordinary objects and logging URLs are not automatically treated as requests. This narrow analysis intentionally sacrifices coverage; exit 0 still means partial review, never compliance.

Review JSON now uses schemaVersion:2 (urn:ex-api-rules:report:2); the core reader and SARIF serializer still accept historical report v1. Readers expecting v1 must explicitly adopt the v2 contract. The v1 schema is unchanged; no CLI downgrade silently discards v2 status/hash data. This is an unreleased working-tree change: the existing 0.2.1 tool metadata is a development snapshot, not a replacement for the published 0.2.1 assets.

Review reads at most 1 MiB per file and 16 MiB per run by default, in 64 KiB chunks. Set --max-file-bytes (1..16777216) and --max-total-bytes (1..268435456) explicitly for another bounded policy; zero/unlimited, fractions and exponent notation are rejected. Files are deduplicated and sorted by UTF-16 path order. A file whose stat size cannot fit the remaining budget is skipped without content reads; later smaller files can still fit. Unsupported files within the same limits are hashed in chunks without keeping the whole file in memory. Limits also bound actual reads if a file grows after stat. Failed read attempts reserve the requested bytes conservatively when the consumed count is unknown; budgetBytesCharged can therefore exceed confirmed bytesRead.

codeVersion.files records adapter, analysisStatus, adapterStatus, reason, size, confirmed bytes, charged budget and hashStatus. Only a complete bounded read with stable observed descriptor/path metadata publishes sha256; skipped, changed or incompletely read input has sha256:null and an explicit reason. Parse/analysis failures can retain a complete hash while remaining unanalyzed. No partial/fake digest is published. These metadata checks do not create an OS snapshot against concurrent replacement.

coverage.selectedRules/excludedRules are an inventory, not business correctness coverage. checkApplicability states are ran (a supported narrow check ran), partial (some checks/data flow unresolved), manual-only, not-applicable (no selected rule or supported static context), and not-run. They are recorded independently of findings: a zero-finding check may have run, and a file with no completed adapter cannot claim an executed check. Unsupported, parse-failed and every other unanalyzed input remain listed with manual reasons. JSON and SARIF retain partial outcome, file statuses, policy and manual checks; exit 0 never proves compliance. Only documented P1 findings change review exit to 1; operational/option errors remain exit 2.

--base includes changed tracked paths and untracked paths not excluded by Git ignore rules; deleted, private/external, unsupported and budget/read/parse failures are represented explicitly. Ignored untracked files are outside this selection and are not enumerated. Explicit --files can select a public ignored file, but explicit private/external paths are rejected before reads. No glob engine or implicit include/exclude expansion is applied.

## Updating intentionally

1. check-updates compares live public sources with this project's pinned evidence and writes external cache/report only. Network failure is incomplete, never unchanged. It reports technical, requires-review, examples/presentation, moved, removed and parse/network failures plus affected rules, endpoints, targets and tests. HTML link/code changes retain before/after evidence and require review, including labelled examples and code indentation. A redirect already present in the baseline is not a new source move. summary.reviewRequired counts all flagged changes (including technical/failure/moved changes); nonTechnical excludes them. status complete means fetching/parsing completed, not that a maintainer approved the changes.
2. On request collect creates a new candidate. Maintainer reads the diff and actual citations, edits authoring rules as needed, and reviews through PR.
3. On explicit approval run approve --candidate ID --reviewed-by NAME. This selects a maintainer bundle only; projects stay pinned.
4. Publish a new immutable bundle; consumers import it, choose pin --bundle ID explicitly, review their code and commit the changed lock separately. To roll back, pin the previous immutable bundle with its compatible tool.

For offline use install dependencies and import bundles in advance. Review performs no network access and does not claim sources are current. check-updates is the only comparison command; neither it nor review executes account requests or source code. Never provide account credentials to this tool.
